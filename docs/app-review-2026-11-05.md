# Life Minder app review — November 5, 2026

## Scope and conclusion

Reviewed the Android entry point, alarm/notification lifecycle, shared screens, tasks/projects, Today/Upcoming, recommendations, routines, medications, events, timers, reviews, trips/checklists, Pixel Studio, persistence, import/export, and release configuration. Findings below come from source inspection; the alarm changes also have automated JVM and Android emulator coverage. This is not a claim of exhaustive physical-device, accessibility, or manufacturer-specific testing.

The app has broad offline functionality. The most valuable next work is reliability and data safety: make backup/import atomic, centralize all background scheduling, and make completion/undo behave consistently across screens. Adding more organizer categories should follow those repairs.

## Completed in this change

- Snoozed alarms have Stop snooze and acknowledgment controls. Alarm activity retains unresolved older alarms and supports acknowledgment after disabling.
- Disable remains separate from acknowledgment; repeating alarms can be disabled entirely or have just the active occurrence finished.
- Each enabled standalone alarm due within two hours has a quiet notification with Skip (Stop snooze for snoozed alarms) and +5 minutes. Different alarms have independent controls; repeated delays apply to only that occurrence.
- Skipping a daily occurrence keeps the next day's normal alarm. Snoozes and delays retain a separate regular timestamp, including across restart and JSON export/import.
- Daily is a direct repeat choice. Older daily-rule encodings remain supported.
- Android clock-alarm recurrence uses local calendar days/weekdays/months, rather than approximating months as 30 days. Ordinary daily alarms retain their local time across daylight-saving changes.
- Old notification action tokens are rejected after the occurrence changes. Alarm transitions reload the current row and serialize receiver/screen changes.
- Notification/in-app dismissal stops an already displayed alarm surface. Database changes from receivers invalidate the open app's observers.
- Re-enabling an expired one-time alarm requires editing its time. Repeating alarms catch up to the next occurrence.
- Database schema 15 adds nullable regular-time/skip-history fields with a nondestructive migration. JSON format 6 retains these fields and accepts versions 1–5.

## Findings to address next

P1 means a reliability or data-loss risk; P2 means incorrect or materially confusing behavior; P3 means polish or a release/process gap. These findings remain open unless explicitly listed as completed above.

| P1 | Raw backups can capture inconsistent data. The live database, WAL, and shared-memory files are copied separately while writes can continue. A valid SQLite header does not prove that the backup is consistent or complete. | `AndroidDataFileGateway.kt`, `backupDatabase()` (line 33). Use a coordinated SQLite snapshot/checkpoint strategy, include Pixel Studio consistently, and verify a restored copy with integrity checks. |
| P1 | Restore and delete leave live screens holding a closed database; pending Android alarms/reminders are not reconciled. Restore copies over files in place and reports a rollback path rather than restoring it automatically on failure. | `AndroidDataFileGateway.kt`, `restoreDatabase()` / `deleteAllLocalData()` (lines 47/74), Settings danger actions in `GeepsControlApp.kt`. Block further editing during replacement, close every database connection, restart the app cleanly, and cancel/rebuild system work from restored records. |
| P1 | JSON imports are not atomic. An error after earlier writes can leave partial imported data, even though Settings says “Import rejected before changes.” Duplicate checks only cover some tables; preset references and alarm-associated IDs are not comprehensively validated/remapped. | `DataPortability.kt`, `importValidated()` (line 335), `decodeAndValidateExport()` (line 406), standalone-alarm import at line 362. The receiver interprets the number as a medication ID; it may find the wrong medication or generate a duplicate future occurrence. ## Missing features and usability opportunities

1. **A single occurrence history and correction model:** show what ran, was skipped, was acknowledged, or was corrected, with Undo where practical. Alarm rows currently retain only their most recent trigger/dismiss/skip timestamps.
2. **Alarm exceptions:** vacation pause, skip until a chosen date, weekday/weekend shortcuts, and an option to change the two-hour notification window. The newly added Skip covers the immediate daily-alarm request.
3. **Timer notification controls:** running countdown, Pause/Resume, +1/+5 minutes, and Finish directly in the notification shade. This change adds upcoming-alarm controls, not a running-timer notification service.
4. **Accessible backup/import:** Android file picker, Share/Save to a chosen folder, backup selection/preview, and clear merge-versus-replace choices. Current organizer import expects one fixed filename in app-specific storage; Pixel Studio already has a more familiar picker workflow.
5. **Archives and global search:** an obvious way to find archived projects/completed history and search across reminders, routines, medications, trips, and tasks.
6. **Travel editing:** validated time-zone picker with side-by-side home/destination times, real attachment bundles, and clear editing of transportation/lodging detail fields. Attachment support is already explicitly deferred.
7. **Discoverability:** make “Timers & Alarms” visible in navigation, show the next alarm prominently, and provide one consistent menu for edit, disable, skip, acknowledge, and delete.
8. **Recovery feedback:** explain failures where they happen, retain unfinished editor input on rotation/process recreation, and replace misleading “failed safely” messages with precise outcomes and recovery actions.

## Suggested sequence

1. Repair backup/restore/import and add failure-injection/round-trip tests.
2. Centralize task/reminder/medication/routine/trip scheduling, cancellation, reboot recovery, and duplicate prevention.
3. Fix timer pause/completion and recurring-task Undo.
4. Unify calendar/time-zone arithmetic and correct conflict detection.
5. Run a focused accessibility and usability pass before adding more features.

## Validation and limits

Final validation passed: 63 shared/JVM tests, 6 Android alarm integration tests, 7 database integration/migration tests, debug APK assembly, and Android lint (with existing warnings). Targeted Android tests cover real notification PendingIntent actions, independent simultaneous alarms, stale buttons, acknowledgment persistence and live database observers, legacy snooze recovery, snooze limits, calendar arithmetic, and schema migration. The emulator runs Android 16/API 36. Repository-wide Spotless does not pass because of existing formatting/line-ending issues; the new Kotlin files were formatted separately and the changed-file whitespace check passes.

Physical-device lock-screen audio, Doze, reboot, OEM battery policies, denied notification permission, and TalkBack/large-font interaction still need hands-on acceptance testing. Upcoming notices are advisory and use inexact scheduling; the ringing alarm keeps the existing exact-alarm path when Android access is granted. Users can control the Upcoming alarms channel in Android settings. See the Android documentation for [notification actions](https://developer.android.com/develop/ui/compose/notifications/create-notification) and [AlarmManager scheduling](https://developer.android.com/reference/android/app/AlarmManager).
